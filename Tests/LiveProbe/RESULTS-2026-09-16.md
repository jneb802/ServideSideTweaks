# Valdev live validation, 2026-09-16

## Result

The header filter removes the redundant `ZPackage` construction for unrelated
incoming requests in the real Unity server. This is not a production crash fix
claim and does not establish a reduction in retained server memory.

## Fixed workload

Each client sent 5,000 requests containing a 128-byte array, then 2,000 containing
a 4,096-byte array. The rates were 10 and 1 messages per rendered frame,
respectively. These custom requests used Valheim's normal routed network path.
The server checked sequence numbers and every byte of each received array.

| Payload array | Requests | Baseline extra packages | Candidate extra packages | Baseline measured allocation | Candidate measured allocation |
|---|---:|---:|---:|---:|---:|
| 128 bytes | 10,000 | 20,000 | 0 | 21,920,608 bytes | 0 bytes |
| 4,096 bytes | 4,000 | 8,000 | 0 | 40,001,232 bytes | 208 bytes |

Every measured request arrived. Both runs recorded zero invalid payloads or
sequence errors. Package construction was counted inside the actual
ServerSideTweaks prefix, not across the entire receive path.

The base game's `RoutedRPCData` first initializes an empty parameter package.
Its `Deserialize` method then replaces that with `ReadPackage()`'s new package.
Skipping that unnecessary decode avoids both package objects.

The native allocation counter is process-wide. Its 208-byte candidate reading
can include concurrent allocations from other threads; it does not identify
those bytes as allocations made by the prefix. The package count has exact
thread-local attribution. The local per-thread allocation test independently
measured zero bytes for the optimized unrelated-request path.

The first candidate small-payload phase included four warm-up requests across
its boundary. It also measured zero packages and zero allocation. The reported
10,000-request result is the clean repeat, `candidate128_repeat_start`.

## Whole-server memory and garbage collection

| Workload window | Baseline server allocation | Candidate server allocation | Collections, baseline / candidate |
|---|---:|---:|---:|
| Small payload | 314,563,552 bytes over 57.6 s | 247,727,864 bytes over 35.5 s | 1 / 1 |
| Large payload | 574,146,664 bytes over 97.0 s | 671,770,120 bytes over 114.8 s | 2 / 2 |

These include all background activity and monitoring. The windows have different
durations, and the clients did not occupy identical positions throughout both
runs. They are not controlled measurements of total allocation savings, server
throughput, or long-term RAM growth. In particular, the candidate large-payload
window allocated more across the whole server because the window and other work
were different. That does not change the directly counted removal of redundant
packages in the inspection step.

Boehm exposes the same collection count through all three managed generation
indices here. Do not add the three columns together.

During the candidate travel phase, 23:01:12–23:03:23 UTC:

- Server working set changed from 4,863,774,720 to 4,859,883,520 bytes.
- Managed memory changed from 2,310,172,672 to 2,281,275,392 bytes.
- Two garbage collections completed. No server crash occurred.
- Samples spanning 23:01:01–23:03:56 show ownership entries increasing from
  15,614 to 26,175 while the working set stayed near 4.53 GiB.

The ownership-entry increase is still present with this optimization. The test
does not show that these numeric records cause a mark-stack overflow.

## Gameplay and routing coverage

- Baseline and candidate both returned the boss-location discovery response.
- Candidate boss announcements reached the nearby second client. At approximately
  940 m separation, the boss announcement did not reach that client. An ordinary
  global message still reached it. The configured boss-message range was 120 m.
- Server-addressed door and pickable requests were submitted after explicitly
  assigning those test objects to the server. The door request created three
  packages in the prefix, including the rewritten forwarded request. The pickable
  request entered the inspected/consumed path.
- A later client object inspection confirmed the same door's stored state was
  `1` (open), then `0` after another server-addressed `UseDoor`. The mushroom's
  stored `picked` flag was `True`.
- Creature spawning and a two-client travel sequence were exercised. Each of the
  two 30-creature requests was limited by the existing client tool to 20 spawns.
  The attempted removal checks found zero matching creatures, so those commands
  are not proof that removal was exercised successfully.
- A later test at an unprotected location placed a `wood_floor` through the
  normal hammer build system (`placed=True`, `status=Valid`). Damage removed it;
  the next object inspection found no matching floor. The build attempts at
  earlier locations returned `NoBuildZone` and `PrivateZone`, respectively.
- At that unprotected location, another 20 Greydwarfs were spawned and one was
  damaged. The removal command then reported 23 matching creatures destroyed
  (including nearby existing creatures). A following inspection found none.
- Travel requested eight destinations per client. Client 01 reached seven
  distinct requested destinations; one request overlapped a pending teleport.
  Client 02 reached five destinations, then remained in teleport-loading state
  at `(-2400, 100, 2400)`. The server stayed up. The complete travel sequence is
  **not** a pass, and its cause was not established by this test.

Both clients subsequently reported the same door ID, owner, and closed state.
After client 02 sent another server-addressed `UseDoor`, both reported state `1`.
Both also reported the same mushroom ID with `picked=True`. See
[the captured object-state output](Evidence/object-state-proof.txt).

Client 02 used a fresh development character for that final check after its
earlier character remained unable to complete loading at the travel destination.

## Setup failures and limits

- Early probe builds hit private-member access errors. Those runs were discarded
  before measured workloads. The final server probe used public package methods
  and public routed-call overloads.
- The server initially rejected the test probe because it was not allowed in the
  test profile's mod policy. Only that isolated policy was updated.
- Disposable world copies exhausted Valdev's disk during candidate preparation.
  The test server was stopped, the disposable copies were removed, and the new
  candidate copy was verified byte-for-byte against its source before startup.
  This failure happened outside both measured workload windows.
- Existing RecipeManager `DisablePiece` null-reference errors appeared in the
  baseline and candidate environments. Shader/headless-rendering errors and
  FastLink example-host DNS errors also occurred. No incoming-inspection,
  dispatcher, or probe access exception occurred during the measured workloads.
- Final client logs also contain aborted dungeon-room loads, a report that six
  of 31 rooms were dropped, and Unity errors about creating objects under a
  parent being destroyed. These occurred around asynchronous dungeon loading
  and teardown, including 23:12:50 UTC, before the final logout. They were retained
  in the private evidence. Their cause and relationship to the travel-loading
  failure are not established. The complete client logs are not error-free.
- Two clients and a short run cannot validate 60-player behaviour, multi-hour
  stability, or production GC crash causation.
- Trophy-block enabled/disabled gameplay, all mining/tree/harvest handlers,
  fermenter handoff, and inventory-item crafting are not yet
  covered by this live run. Header/configuration decisions have local automated
  coverage, which is not equivalent to those gameplay checks.
